# Creating a new AWS account for the stack

A step-by-step guide to a fresh AWS account with the simplest workable setup: one **root user**
(billing and rare root-only tasks) and one **IAM user `admin`** (deploys and daily work). No
Builder ID, no AWS Organizations, no IAM Identity Center, no access portal.

What to do after the account exists (deploying, daily routine) is in `docs/RUNBOOK.md`; this
document only covers getting there. As everywhere in this public repository: no e-mail
addresses, account ids or passwords in here. Keep them in your password manager.

---

## 0. The one rule: use "Sign up for AWS (advanced)"

AWS now has two sign-up flows, and the difference is exactly the problem you hit with the first
account:

| | Sign up for AWS **(new)** | Sign up for AWS **(advanced)** |
|---|---|---|
| Start URL | `https://signin.aws.amazon.com/signup?request_type=builderId` | `https://signin.aws.amazon.com/signup?request_type=register` |
| Owner of the account | A **Builder ID** ("You do not create a root user. Your AWS Builder ID owns your project accounts") | A classic **root user** (e-mail + password) |
| Also created for you | An **Organization**, **IAM Identity Center**, "projects", an access portal | Nothing: a standalone account |
| Region | Picked by AWS | You choose |

The first account was created through the **new** flow, which is why it has an Organization,
an access portal and a Builder ID that cannot be deleted. Everything below uses the
**advanced** flow. Two consequences:

- **Open the advanced URL directly.** Do not start from the AWS home page, Builder Center or a
  "Get started" button: those lead to the new flow.
- **Use a fresh e-mail address for root, one that has never had a Builder ID.** A Builder ID is
  bound to an e-mail address, and an address with one makes the sign-in page ask "Builder ID or
  root?" every time. A new plus-address (`you+aws-hello-root@gmail.com`) works.

What you need before starting: that fresh e-mail address, a phone that can receive an SMS, a
credit card (the advanced flow refuses to continue without a payment method; a 1 USD hold is
placed and released), a password manager, and an authenticator app for MFA.

---

## 1. Create the account (about 10 minutes)

1. Open `https://signin.aws.amazon.com/signup?request_type=register`.
2. Enter the **root user e-mail address** (the fresh one) and an **account name**, for example
   `hello-world-api`. Click **Verify email address**, enter the code from the e-mail.
3. Set the **root password**: generated by the password manager, stored there immediately.
4. **Account plan:** choose **Paid**. The Free plan only allows "Always Free" services and
   closes the account after six months unless upgraded; this stack is meant to stay. The real
   cost of the stack is cents per month (architecture section 8), and step 5 creates a 1 USD
   budget alarm.
5. Contact information: choose **Personal**, fill in the address and phone number, accept the
   Customer Agreement.
6. Billing information: the credit card.
7. Identity confirmation: SMS code.
8. Support plan: **Basic** (free).
9. **Complete sign up**, then wait for the "account activated" e-mail (minutes, up to 24 h).

You now have an account whose only identity is root. Do not deploy anything with it.

---

## 2. Secure root and open billing to the admin user (root, once)

Sign in at `https://console.aws.amazon.com/` → **Root user** → the root e-mail and password.

1. **MFA on root.** Top right, account name → **Security credentials** → **Multi-factor
   authentication (MFA)** → **Assign MFA device** → **Authenticator app**. Store the recovery
   secret in the password manager.
2. **Let IAM users see billing.** Account name → **Account** → **IAM user and role access to
   Billing information** → **Edit** → **Activate**. Without this, the `admin` user cannot
   open Billing → Budgets, and `npm run budget` fails with an access-denied error.
3. **Note the account id** (12 digits, account name menu, top right). It goes into the
   password manager, next to the root entry. The admin user signs in with it.
4. Optional: **Account alias**. IAM → Dashboard → **Account Alias** → **Create**, for example
   `hello-world-api`. The admin sign-in URL then reads
   `https://hello-world-api.signin.aws.amazon.com/console` instead of
   `https://<account id>.signin.aws.amazon.com/console`.
5. **Sign out.** Root is now used only for: billing settings and payment method, closing the
   account, changing root's own password or MFA, resetting the admin user if it locks itself
   out, and account-level settings (contacts, regions). Never create root access keys, never use
   root from the CLI.

---

## 3. Create the admin user (root, once)

Still signed in as root. The IAM console pushes towards Identity Center at every turn; refuse it
each time.

1. IAM → **Users** → **Create user**.
2. **User name:** `admin`. Tick **Provide user access to the AWS Management Console**. On the
   question that follows, choose **I want to create an IAM user** (not "Specify a user in
   Identity Center").
3. **Console password:** **Custom password**, generated by the password manager. Untick
   **Users must create a new password at next sign-in**. Next.
4. **Permissions:** **Attach policies directly** → search `AdministratorAccess` → tick the AWS
   managed policy of that exact name. Next → **Create user**.
5. Open the new user → **Security credentials** → **Multi-factor authentication (MFA)** →
   **Assign MFA device** → **Authenticator app**. MFA is what makes a single all-powerful user
   acceptable here.
6. **Do not create access keys.** The CLI signs in through the browser (section 4), with
   credentials that expire on their own. There is nothing to rotate or leak.
7. Sign out of root.

Why one `AdministratorAccess` user and not something narrower: SAM creates and deletes IAM
roles, Lambda functions, API Gateway, Cognito, DynamoDB, CloudWatch alarms and SNS topics, and
the operator scripts read CloudFormation outputs and write Budgets. A narrower policy would
need maintenance at every plan step for no gain while a single person operates the account.
The architecture's "no wildcard" rule applies to the function roles in `template.yaml`, not to
the human operator.

## 4. Sign the CLI in as the admin user (each machine, then each day)

`aws login` (AWS CLI 2.32.0 or later; the Codespace has 2.39.2) signs the CLI in through the
browser as the IAM user and keeps short-lived credentials, refreshed automatically for up to
12 hours. No access keys on disk.

1. In `~/.aws/config`, replace the Identity Center profile with a plain one:

   ```ini
   [profile hello-admin]
   region = eu-north-1
   ```

   Delete the old `[sso-session hello]` section and the `sso_*` lines. Keeping the profile
   **name** means every command in `CLAUDE.md` and the runbook stays valid.

2. Sign in. In the Codespace there is no browser callback, so use the remote (device) flow:

   ```bash
   aws login --profile hello-admin --remote
   ```

   The command prints a URL and a code. Open the URL, enter the code, and on the sign-in page
   choose **IAM user**: account id (or alias), user name `admin`, password, MFA code. On a laptop
   with a browser, `aws login --profile hello-admin` opens the page by itself.

3. Verify:

   ```bash
   export AWS_PROFILE=hello-admin
   aws sts get-caller-identity
   # "Arn": "arn:aws:iam::<account id>:user/admin"
   ```

When a later command fails with an expired-credentials error, run step 2 again. That replaces
`aws sso login --profile hello-admin --use-device-code` in the runbook's daily routine.

---

## 5. Deploy the stack

From here the runbook applies unchanged, section 3 "Deploying from scratch": `local:up` +
`local:api`, `npm run verify`, `npm run deploy -- --parameter-overrides AlertEmail=<address>`,
confirm the SNS subscription e-mail, `npm run bootstrap-admin hello-world-api`,
`npm run budget hello-world-api`, `npm run smoke hello-world-api`.

Two things are simpler than in the first account:

- **Region:** `eu-north-1` stays (it is in `samconfig.toml`), but only out of habit. This
  account has no organization policy restricting regions.
- **Billing → Budgets** in the console works for `admin` as soon as root did step 2.2.

## 7. The old account

Leave it alone until the new one is deployed and smoke-tested. Then, if you want it gone:
sign in with the Builder ID at AWS Settings and close the project (`hello-world-api` stack
first, `sam delete`, so nothing keeps billing). Closing it is the only way the Builder ID can
be deleted (`docs/AWS_ACCOUNTS.md` section 5). Not part of this guide; ask when you get there.

## Daily routine, for reference

| You want to | Sign in as | Where |
|---|---|---|
| Deploy, smoke test, read logs, Cognito, the table, budgets | `admin` | Console: `https://<alias or account id>.signin.aws.amazon.com/console`; CLI: `aws login --profile hello-admin --remote` |
| Change the payment method, close the account, fix a locked-out `admin` | root | `https://console.aws.amazon.com/` → Root user |
| Anything with a Builder ID | nobody | This account has none |
