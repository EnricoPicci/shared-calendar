## 2. The two files that split

### 2.1 `src/lib/validation.ts` → `shared/src/username.ts` + `backend/src/lib/validation.ts`

To `shared/src/username.ts` (new):

```ts
import { z } from 'zod';

// Architecture section 4: 3 to 32 characters, lowercase, starting with a letter or digit.
export const USERNAME_PATTERN = /^[a-z0-9][a-z0-9._-]{2,31}$/;
export const Username = z.string().regex(USERNAME_PATTERN, 'invalid username');

// .strict() rejects unknown fields, e.g. an attempt to pass { "group": "admin" }.
export const CreateUserBody = z.object({ username: Username }).strict();
export type CreateUserBody = z.infer<typeof CreateUserBody>;

// An object rather than the bare string, so that a rejection names the field.
export const UsernameParam = z.object({ username: Username });
export type UsernameParam = z.infer<typeof UsernameParam>;
```

Stays in `backend/src/lib/validation.ts`: `validate<T>(schema, value): Outcome<T>` unchanged
(it imports `error`/`Outcome` from `./http` and `z` from `zod`; it no longer declares any
schema).

Tests: `tests/unit/lib/validation.test.ts` is written against `validate(CreateUserBody, …)`,
so it tests both the schema and the helper at once. Split it like this:

- `shared/tests/username.test.ts` (new): `CreateUserBody.safeParse(...)` / `UsernameParam.safeParse(...)`
  for: accepts valid names; rejects uppercase, too short, too long, bad first character;
  rejects unknown fields; rejects a missing username; rejects a non-object.
- `backend/tests/unit/lib/validation.test.ts` keeps what is about the **response**: 400 with
  `invalid_request`, the field list in the message (`username`, unknown keys named
  individually, `(root)` for a non-object), and "never echoes the rejected value". It imports
  `CreateUserBody` from `@shared-calendar/shared` and `validate` from `../../../src/lib/validation`.

### 2.2 `src/lib/auth.ts` → `shared/src/roles.ts` + `backend/src/lib/auth.ts`

To `shared/src/roles.ts` (new):

```ts
export type Role = 'admin' | 'user';

// Architecture section 3: admin wins over user; in neither group means no role.
export function resolveRole(groups: readonly string[]): Role | null {
  if (groups.includes('admin')) return 'admin';
  if (groups.includes('user')) return 'user';
  return null;
}
```

Stays in `backend/src/lib/auth.ts`: `Claims`, `getClaims`, `requireGroup` and the zod schemas
of the authorizer context, with `import type { Role } from '@shared-calendar/shared'` for the
`requireGroup(claims, group: Role)` signature.

Tests: `describe('resolveRole', …)` of `tests/unit/lib/auth.test.ts` (the four group
combinations: admin, user, both, none) moves as it is to `shared/tests/roles.test.ts`. The
rest of the file stays.

**To confirm at step 5, because it is the one assumption not yet tested on this machine:**
`sam build --build-in-source` with the esbuild build method is the documented way to build
inside a workspace, but SAM may still run `npm install` in `backend/` before bundling. In a
workspace folder npm walks up to the root manifest, so that should be harmless; if it is not
(a `backend/node_modules` appears or the build fails to resolve `@shared-calendar/shared`),
the fallback is to set `CodeUri` to `../` in `template.yaml` with `EntryPoints` prefixed by
`backend/`, which lets SAM copy the whole repository (slower, and `.aws-sam` must then ignore
`frontend/` and `node_modules`). Record whichever works in `docs/FOLDER_STRUCTURE.md` 4.3.
